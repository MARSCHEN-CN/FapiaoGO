## 0. 一句话结论

**「还能优化多少」完全取决于你的发票构成，两者差一个数量级：**

| 你的发票构成 | 剩余优化空间 | 性质 |
|---|---:|---|
| 全是**矢量 PDF**（电子发票） | **30%~98%，但绝对量只有几十~几百毫秒** | 锦上添花 |
| 含**拍照 / 扫描件** | **1.9× ~ 29×（秒级 → 亚秒级）** | 救命 |

⚠️ **你已测的 27 次切换，全部是矢量 PDF，一张图片都没有。**
所以「已测速度可接受」这个判断**不能**推广到你的原始痛点。

## 1. 你测的是什么：矢量 PDF，不是你的原始痛点

真机数据 `natural` 列全部是 `1241x827` 级别。反推源尺寸：

```
1241 ÷ 2.083 = 595.7 pt   （zoom = preview dpi/72 = 150/72 = 2.083）
 827 ÷ 2.083 = 397.0 pt
```

`595 × 397pt` = A4 宽 + 约 140mm 高 = **标准增值税发票版式**。
若是拍照/扫描件，会被 `zoom=150/72` 放大 1.5625 倍，输出**不可能**是这种整 pt 尺寸。

沙箱构造 595×397pt 矢量 PDF 走真实链路，输出 **1240×828** —— 与真机 `1241×827` 吻合，推断已验证。

**⇒ R1（位图输出失控）在你这批样本里 100% 未被覆盖。**

## 2. 场景 A：矢量 PDF —— 剩余空间逐项拆解

真机 27 次采样的三档耗时：

| 档位 | T1→T4（资源获取） | 场景 | 天花板 |
|---|---:|---|---|
| 🟢 稳态 | **6~8 ms** | 第 3 次起（memory cache） | **已到极限，无空间** |
| 🟡 第 2 次 | **313 ms**（固定，重复 3 次） | 后端已热、浏览器仍需处理 | **目标 ~7 ms** |
| 🔴 首次 | **150~750 ms** | 后端冷渲染 / 排队 | 目标 ~150~300 ms |

分层占比：**96% 在 T1→T4**，decode 仅 5~12ms、T5→T6 仅 0~26ms。

### 2.1 稳态（6~8ms）—— 别再动它

这条路径已经是浏览器 memory cache 直出。**理论下限就是几毫秒**，任何优化都无意义。

### 2.2 第 2 次（313ms）—— 最大的剩余项，但成因**未证实**

`313.3 / 313.7 / 313.9` 三次几乎相同 ⇒ **固定开销，不是抖动**。

已排除后端：本轮实测同源矢量 PDF，后端 + HTTP 全程 **2~3ms**，与 313ms 差**两个数量级**。

两个候选（**均为嫌疑，未单变量验证**）：

1. **HTTP/1.1 连接池排队** —— 每域名 6 连接，一次切换发 展示区 1 + RE probe 1 + 预取 ±3（最多 6）= **最多 8 个请求**，必然排队
2. **`must-revalidate` 落盘 I/O** —— `api.py:141` 设 `max-age=0, must-revalidate`，每次 304 后都要更新磁盘条目

**零成本验证**（开关已落地，DevTools 单行）：
```text
localStorage.setItem('fapiao.perf.disableFrontendPrefetch','1')
```
若 313ms 档消失 ⇒ 确认是排队。

### 2.3 首次（150~750ms）—— 后端冷渲染是硬下限

本轮实测矢量 A4 冷渲染 **294.8ms**（真实 engine）。
观察到的 150ms 档 = 被预取提前渲染过（后端已热）；500~750ms 档 = 真冷 + 排队。

**这里有个结构性矛盾**（R2 的本质）：

```
预取能加速「首次」    → 但会拖慢「后续」（+113% 实测）
关掉预取能消除 313ms  → 但「首次」会退回 500~750ms
```

**⇒ 正确答案不是关掉预取，而是 QoS 隔离**（行为契约已冻结：Foreground 不得被 Prefetch 显著拖慢；实现方案 5 选 1 未冻结）。

### 2.4 场景 A 上限汇总

| 指标 | 现状 | 可达 | 手段 |
|---|---:|---:|---|
| 稳态 | 6~8 ms | 6~8 ms | 无空间 |
| 第 2 次 | 313 ms | ~7 ms | 消除排队（关预取 / QoS） |
| 首次 | 500~750 ms | ~150~300 ms | 预取 QoS 隔离 + R3 |
| 首次 | 500~750 ms | ~350~690 ms | 仅 R3（墙钟 -8~30%） |

**场景 A 能做到最好：所有已看过的切换 ≤10ms，未看过的 ≤300ms。**

## 3. 场景 B：拍照 / 扫描件 —— 真正的大头（本轮新实测）

本轮实测「现状 vs 长边上限 `MAX_LONG_EDGE=2000`」，交叉验证 **0.0% 误差**（复现路径与真实 engine 字节级一致）⇒ 数字可信。

| 样本 | 现状产物 | 现状耗时 | 新策略产物 | 新策略耗时 | **提速** |
|---|---|---:|---|---:|---:|
| 扫描件 1240×1754 | 1938×2741 · 508KB | 1189 ms | 1240×1754 · 370KB | 614 ms | **1.9×** |
| 高拍仪 2592×1944 | 4050×3038 · 1167KB | 2622 ms | 2000×1500 · 445KB | 854 ms | **3.1×** |
| 手机拍照 3000×4000 | 4688×6250 · 2.8MB | 6807 ms | 1500×2000 · 421KB | 958 ms | **7.1×** |
| 手机拍照 4608×3456 | 7200×5400 · 3.9MB | 27725 ms | 2000×1500 · 387KB | 957 ms | **29.0×** |

体积同步下降 **1.4× ~ 10.1×**（16MP：3.9MB → 387KB）。

### 3.1 策略公式（与用户复核意见一致）

```python
# 位图：不放大，只缩小
src_max_px = max(pr.width, pr.height) * 96.0 / 72.0
scale      = min(1.0, MAX_LONG_EDGE / src_max_px)
zoom       = (96.0 / 72.0) * scale

# 矢量：仍走 preset.dpi / 72（不变）
```

实测放大倍数：扫描件 `1.563× → 1.000×`（不放大，符合预期）、12MP `→ 0.500×`、16MP `→ 0.434×`。

### 3.2 必须区分位图 / 矢量 —— 实测证明

若把位图公式误套到矢量上：

```
矢量 A4 现状(dpi/72)   : 1240×1755   zoom=2.083
矢量 A4 误用(位图公式) :  794×1123   zoom=1.333
⇒ 输出宽度比 0.640×（面积 0.41×）
```

**矢量清晰度会掉到 41%，这是不可接受的退化。** 契约必须写明两者走不同策略。

### 3.3 阈值敏感性（12MP）

| MAX_LONG_EDGE | 产物 | 耗时 | 体积 |
|---:|---|---:|---:|
| 1200 | 900×1200 | 489 ms | 61 KB |
| 1600 | 1200×1600 | 618 ms | 240 KB |
| **2000** | 1500×2000 | 931 ms | 422 KB |
| 2400 | 1800×2400 | 1216 ms | 628 KB |

**推荐 2000**：展示区实际显示宽约 800~1200px，2000 已留足缩放余量；1600 可再省一半体积（240KB）若更看重流量。

## 4. 锦上添花候选（按 收益 / 风险 排序）

| 优先级 | 项 | 对矢量场景收益 | 对图片场景收益 | 风险 | 状态 |
|---|---|---|---|---|---|
| 🟢 P0 | **关前端预取验证 313ms** | 可能 -306ms | — | **零**（开关已就绪） | 立即可验 |
| 🟢 P0 | **R3 消除 RE probe** | 首次 -8~30% | 同左 + 减半 CPU | 低（开关已就绪） | 立即可验 |
| 🟠 P1 | **R1 位图长边上限** | **零** | **1.9× ~ 29×** | 契约级（须同步 `RENDER_ENGINE_VERSION`） | 待 Phase 3 |
| 🟠 P1 | **预取 QoS 隔离** | 首次 750→~150ms | 同左 | 中（架构改动） | 行为契约已冻结，方案未冻结 |
| 🔵 P2 | dimensions cache | **极小**（T5→T6 仅 0~26ms） | 同左 | 中 | **建议降级** |
| ⛔ — | immutable 缓存 | 低 | 低 | **高** | **已否决**，见 §5 |

### 4.1 ⚠️ 反直觉结论：dimensions cache 收益极小

此前（包括我）都把「`setNaturalDims(null)` 导致重新 loading」当成重要根因。
但真机数据说：**T5→T6 只有 0~26ms**，而 T1→T4 是 150~750ms。

```
T1→T4  96%   ← 全部问题在这里
T4→T5  ~2%   （decode 5~12ms）
T5→T6  ~2%   （0~26ms）  ← dimensions cache 只能优化这一段
```

**⇒ 优化错地方了。** dimensions cache 仍是「高可信候选」，但**不应优先**——它最多省 26ms，而排队能省 306ms。

## 5. ⛔ 已否决：immutable 缓存

直觉上 `Cache-Control: immutable` 能消除 304 往返，是笔大优化。
**但后端既有注释明确否决**（`api.py:100-103`）：

```
NOTE: /preview does NOT use `immutable` because the current URL does not
include all byte-changing parameters (e.g., isLandscape derived from
page.rect + rotation). Browser caching therefore uses must-revalidate
so that If-None-Match negotiation can correct stale orientation responses.
```

即：**URL 不含 `isLandscape` 等会改变输出字节的参数**，若设 immutable，方向变化后会永久返回错误字节。
且 `make_cache_key` 含 `engine_version`（`cache.py:161`）而 URL 不含 —— 渲染引擎升级后浏览器缓存同样无法失效。

**⇒ 收益低（后端 304 实测仅 2~3ms）、风险高（脏缓存），不建议。**
要启用必须先补齐 URL 参数完整性，属独立改造，不混入本次。
