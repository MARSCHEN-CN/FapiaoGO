## 0. 一句话结论

**没有做任何优化，一行生产代码都没动。**

「感觉没啥问题」是**样本偏差**造成的错觉：这 27 次切换**全部是矢量 PDF 电子发票**，
一张拍照/扫描件都没有，因此 R1（位图过度渲染）的灾难区**完全没被覆盖**。

但数据里确实存在一个**尚未解释的固定慢点（313ms 档）**，且实测已证明
**它不在后端、也不在 HTTP 层** —— 责任在浏览器侧。

## 1. 先回答：为什么「感觉没啥问题」

### 1.1 代码层面：没动过

| 项 | 状态 |
|---|---|
| 生产渲染/加载逻辑 | **零改动** |
| 新增代码 | 仅探针（`previewSwitchTrace.js`）+ 实验开关（`perfExperimentFlags.js`） |
| 开关默认值 | **全部 OFF** —— 合并后行为与改动前逐字节一致 |
| dev 模式影响 | React development build + `StrictMode`，**只会更慢**，不会更快 |

### 1.2 样本层面：没踩到雷区（主因）

`natural` 列全部落在 `1240×826` ~ `1252×828` 区间，典型值 `1241×827`。

反推源尺寸（preview preset dpi=150，输出 = 页面 pt × 150/72）：

```
1241 ÷ (150/72) = 595.7 pt
 827 ÷ (150/72) = 397.0 pt
```

`595 × 397 pt` = **A4 宽度 + 约 140mm 高** —— 标准增值税发票版式。

若是拍照/扫描件（位图），fitz 按 96dpi 包装后再被 `zoom = 150/72` 放大 1.5625 倍，
输出**不可能**是这种整 pt 尺寸。⇒ **这批样本是矢量 PDF，不是位图。**

沙箱复核（构造 595×397pt 矢量 PDF，走真实 preview 链路）：

```
[A] 冷渲染 172.4 ms  fmt=webp bytes=8826  输出尺寸=1240x828
                                          ↑ 与真机 1241x827 吻合
```

**所以 R1 的灾难区（12MP → 6.3s、16MP → 29.3s）在这批数据里根本没出现。**
你之前「等特别久」的体感，大概率来自拍照/扫描件，**那部分还没被测到**。

## 2. 数据里真正有价值的信号

### 2.1 三档耗时

| 档位 | T1→T4 加载 | 出现场景 |
|---|---:|---|
| 🟢 快 | **6 ~ 8 ms** | 同一文档**第 3 次及以后**访问 |
| 🟡 慢 | **313 ms**（固定） | 同一文档**第 2 次**访问 |
| 🔴 最慢 | **150 ~ 750 ms** | 首次访问 |

313ms 这一档重复出现三次：`313.3` / `313.7` / `313.9`
—— 高度一致的数值 ⇒ **固定开销，不是抖动**。

典型序列：

```
#1  4fd9e93a3d  751.8 ms   ← 首次
#14 4fd9e93a3d  313.3 ms   ← 第 2 次
#27 4fd9e93a3d    6.3 ms   ← 第 3 次

#2  5c3987d12b  184.6 ms   ← 首次
#5  5c3987d12b  313.7 ms   ← 第 2 次
#7  5c3987d12b  313.9 ms   ← 第 3 次（仍在 313 档）
#15 5c3987d12b    7.5 ms   ← 第 4 次
```

### 2.2 分层占比：瓶颈 100% 在 T1→T4

| 段 | 实测范围 | 占比 |
|---|---:|---:|
| T0→T1 React 状态传播 | 12 ~ 48 ms | 小 |
| **T1→T4 资源获取** | **6 ~ 752 ms** | **≈ 96%** |
| T4→T5 decode | 4.9 ~ 11.6 ms | 可忽略 |
| T5→T6 可见 | 0 ~ 26 ms | 可忽略 |

⇒ decode 与上屏**都不是**瓶颈。这也说明：只要资源能秒到，UI 就快。

### 2.3 一个待观察的趋势

`T0→T1` 随切换次数单调上升：`#6/#8` 约 12ms → `#22~#26` 约 36~48ms。
可能是 dev 模式 `StrictMode` 放大、也可能是状态/内存累积。
**dev 模式下不作为结论**，若重打包后仍存在需单独立项。

## 3. 313ms 归属：实测排除法

跑 `_phase2_304_bench.py`（构造 595×397pt 矢量 PDF，与真机样本同源）：

| 层 | 实测 | 判定 |
|---|---:|---|
| `engine.render()` RenderCache 命中 | **0.006 ms** | ✅ 排除 |
| HTTP 200（缓存命中，仍回 body） | **2.4 ms** | ✅ 排除 |
| HTTP 304（`must-revalidate` 实际路径） | **2.0 ms** | ✅ 排除 |
| 前台 + spec 变体并发 | **3.0 ms**（+55%） | ✅ 排除 |

**后端 + HTTP 全程只要 2~3 ms。313ms 不在这条链路上。**

同时排除的还有：
- ❌ 后端 304 判定前先渲染（`api.py:604` 确实先 `engine.render()` 再判 304）——
  但缓存命中只要 0.006ms，不构成问题
- ❌ `RenderCache` 存的是**已编码 bytes**（`cache.py:64`），不存在每次重编码
- ❌ R3 双管线竞争：并发实测仅 +55%（1.9 → 3.0 ms），量级差两个数量级

### 剩下的唯一位置：浏览器侧

304 只要 2ms，但 `img` 的 `onload` 要等 313ms ⇒ 中间 ~310ms 花在 Chromium 内部。
最大嫌疑两个（**均为候选，未单变量验证**）：

1. **请求排队** —— HTTP/1.1 每域名并发连接上限 6。
   每次切换发出：展示区 1 + 遗留 RE probe 1 + 前端预取 ±3（最多 6）= **最多 8 个请求**，
   必然排队。6~8ms 那档则是 memory cache 命中、完全不进网络队列。
2. **缓存落盘 I/O** —— `Cache-Control: public, max-age=0, must-revalidate`，
   每次 304 后 Chromium 都要更新磁盘缓存条目（受杀软实时扫描影响会显著放大）。

两者区分要靠 `cache` 列，见下节。

## 4. ⚠️ 探针缺陷（首轮数据 cache 列 100% 不可用）

首轮 27 行全部是 `unknown(no-resource-timing)` —— **这是探针 bug，不是环境问题**。

**根因**：Chrome 的 resource timing buffer **默认仅 250 条**。
vite dev 模式下每个 ES module 都是独立请求，几百个模块在启动时就把 buffer 打满，
之后产生的 `/preview/` 条目**根本不会被记录**。

**已修**（`previewSwitchTrace.js`）：

| 修复 | 做法 |
|---|---|
| 扩容 | 探针开启时 `setResourceTimingBufferSize(5000)`；模块加载期若 flag 已开则立即执行 |
| 自持快照 | `PerformanceObserver({type:'resource', buffered:true})` 在条目产生瞬间拷入自有 Map，不依赖 performance buffer 存活 |
| 兜底查询 | 先查自持快照，miss 再回落到 `getEntriesByName` |
| 负值修正 | decode 的 promise 可能晚于可见帧 resolve ⇒ `t5 > t6` 时 clamp 成 0 |
| 自检行 | `dump()` 输出 `performance.resource=N 自持快照=M observer=true` —— 快照=0 则 cache 列不可信 |

## 5. 下一步：三个单变量实验

### 实验 1（最优先）—— 验证「请求排队」假设

DevTools Console 单行：

```text
localStorage.setItem('fapiao.perf.disableFrontendPrefetch','1')
```

然后 `__fapiaoSwitchTrace.reset()`，按 **A → B → A → B → A** 切，最后 `dump()`。

**判据**：若 313ms 档显著下降或消失 ⇒ 确认为预取占满连接池导致的排队。

### 实验 2 —— 验证 R3 双管线的实际贡献

```text
localStorage.setItem('fapiao.perf.disableLegacyReProbe','1')
```

**判据**：对比开启前后同一序列。注意 KPI 是「每次切换的 `/preview/` 请求数 2 → 1」，
**不是**墙钟减半（Phase 1 已实测墙钟仅省 8~30%）。

### 实验 3（补上缺失样本，最关键）—— 把大图发票纳入

找几张**手机拍照 / 扫描件**发票（不是电子 PDF），对它们做 A → B → A。

**判据**：看 `natural` 是否远超 1241×827（位图会被放大 1.5625 倍），
以及 T1→T4 是否进入**秒级**。这才是你原始痛点「等特别久」的真实场景。

> 三个实验都要求后端带 `RE_TIMING_ALLOW_ORIGIN=1` 启动（否则 `cache` 列仍不可读），
> 且实验 1/2 的开关改完**无需重启**，实验 3 需要重启后端时带上环境变量。
